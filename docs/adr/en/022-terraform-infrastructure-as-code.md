# 022 - Infrastructure as Code with Terraform

## Context

After the README (quick, high immediate value), industrialization
remained the most strategic undertaking for the Data Engineer goal,
with three building blocks planned in the Phase 5 roadmap: Terraform,
Docker, CI/CD. Until now, all of the project's AWS infrastructure
(VPC, subnets, 10 endpoints, security group, IAM accounts, roles,
policies, 2 Lambda functions, 2 EventBridge rules, S3 bucket, Glue
Catalog database, Glue Crawler) had been created **manually**,
click by click in the console, consistent with the project's
pedagogical approach, but with no guarantee of reproducibility or
protection against human configuration error.

## Decision

Import of the entire existing infrastructure (28 resources) under
Terraform via `terraform import`, without ever recreating or
destroying any real resource. Organized into 4 coherent modules:
- `network` (VPC, private subnets, security group, 10 VPC Endpoints,
  route table, the MWAA network foundation)
- `iam` (2 IAM accounts, 2 roles, 2 policies)
- `data-lake` (S3 bucket, Glue Catalog database, Glue Crawler)
- `ingestion` (2 Lambda functions, 2 EventBridge Scheduler rules)

The content of the Lambda code (the deployed zip) intentionally stays
outside the Terraform scope: each function references an empty
`placeholder.zip` with `lifecycle { ignore_changes = [...] }`,
leaving `scripts/build_lambda_*.sh` to handle the application code
deployment, consistent with the principle of separating infrastructure
from code. The Open Charge Map API key is injected through a
`sensitive` Terraform variable, with its real value only in
`terraform.tfvars`, never committed.

## Why

Importing rather than recreating allows taking over an existing
infrastructure with no service interruption, a realistic and common
case in a company, where Terraform is almost never introduced on a
blank project. Every import was systematically followed by a
`terraform plan` manually checked before any `apply`, with a strict
principle: any `-/+` symbol (destroy then create) on a resource
requires stopping and investigating before continuing, never a
reflex `apply`.

The split into modules distributes responsibilities based on their
real function rather than their mere membership in the same AWS
service: the S3 bucket, although used by several other parts of the
project, remains an isolated resource in `data-lake` rather than a
pseudo-module "S3", following the principle that a module groups
resources that are born and evolve together, not ones that simply
share a technology.

## Consequences

The first `terraform plan` on the MWAA security group revealed a
`-/+ must be replaced`, caused by a `description` mismatch that
cannot be modified in place on AWS. Without this systematic check, an
`apply` would have destroyed and recreated this security group with a
new ID, instantly breaking the 9 Interface VPC Endpoints that
referenced it, an incident directly comparable, in severity, to the
network blockers encountered while setting up MWAA (see ADR-021),
this time avoided before it happened rather than diagnosed after the
fact.

Two accepted limits remain outside the Terraform scope: the content
of the Lambda code (managed by the existing build scripts), and the
MWAA environment itself (whose two internal VPC endpoints are
dynamically generated by AWS at creation time, making their upfront
description structurally impossible without a multi-pass mechanism,
see ADR-021 for detail).

The rest of Phase 5 (Docker, CI/CD) will be handled on separate
dedicated branches, consistent with the principle that a branch
represents a complete, functionally independent change, not a
grouping of unrelated topics.
